# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

R4DEV is a Quarto website teaching reproducible data analysis in R (tidyverse-first), created by Nelson Amaya. It is published to Netlify at https://r4dev.netlify.app/ (site id in `_publish.yml`). The site is a workshop organized in four tracks — the core workshop (`sessions_workshop/`), AI · LLMs (`sessions_ai/`), statistical thinking (`sessions_thinking/`), and tools (`sessions_tools/`). Each session is a standalone `.qmd` lesson that downloads real data from the web and builds plots, maps, animations, text analysis, simulations, and Shiny apps. Sessions are numbered per track (`NN-name/NN-name.qmd`, starting at 01 within each track).

## Modernization status (July 2026)

The 2026 modernization (Phases 0–3) shipped and is live at https://r4dev.netlify.app/. `UPDATE_PLAN.md` carries a **Phase 4 ambitious expansion plan**; items done — **4h** (Shiny apps deployed to Posit Connect Cloud and embedded as `<iframe>`s in their sessions; `r4dev-covid19` retired outright, `r4dev-querychat` fixed — see below) and **4d** (the "Ask R4DEV" RAG capstone, `shiny/r4dev-ask` — see below). A new **session 12** (`12-parallel`, purrr + mirai; renamed `sessions_workshop/09-parallel` in the July 2026 naming pass) shipped in Phase 9 — see `UPDATE_PLAN.md`. The rest (causal-methods, data-at-scale, forecasting, packaging/production-Shiny, CI, accessibility) is unstarted, pending scope sign-off. Key outcomes future sessions should know:

- **`r4dev-covid19` was retired, not fixed** — see the terra/GDAL note below for why. Its replacement (`r4dev-earthquakes`, point-based USGS data) is blocked on the same wall: `leaflet` **hard-`Imports` `sf`** (confirmed via `packageDescription("leaflet")$Imports`, not just Suggests) and also Suggests `terra` directly, so `library(leaflet)` alone — with zero polygon/sf code anywhere in the app — still drags `terra` into the Connect Cloud/shinyapps.io build and fails on the same GDAL 3.4.1 mismatch. **This means `leaflet` is currently unusable on both hosting platforms, full stop, regardless of what geometry type the app actually plots.** The fix in principle is pinning an older `terra` (1.8-53 or earlier predates the incompatible multidimensional-GDAL code path introduced in 1.8-54) via a `renv.lock`-based deploy, but attempting this hit an unresolved local blocker (see the R-version/package-ABI note below) — the pragmatic fallback proven to work today is the `plotly` `type="choropleth"`/`scattergeo` technique used for the current `r4dev-covid19`-replacement attempt.

- **`querychat` deployment gotcha (r4dev-querychat)**: `querychat_app()` (the batteries-included convenience wrapper) failed on Connect Cloud with a startup health-check timeout — the app process was actually running (`Listening on http://127.0.0.1:<port>` in the log) but Connect's proxy could never reach it. Root cause: `querychat_app()`'s `$app()` method calls **`shiny::runGadget()`**, which is built for interactive local use (RStudio's viewer pane) and binds its own ad-hoc port unrelated to whatever port a hosting platform's launcher expects to proxy to — it is not meant to be deployed as a standalone Shiny app at all. Fix: use querychat's modular API instead — `QueryChat$new(data, ..., client = ellmer::chat_anthropic(model = "claude-sonnet-5"))` + `qc$sidebar()` (or `qc$ui()`) + `qc$server()` wired into an ordinary `ui <- page_sidebar(...)` / `server <- function(input, output, session) {...}` / `shinyApp(ui, server)` — this builds a plain Shiny app object that Connect's launcher runs normally. `shiny/r4dev-querychat/app.R` now follows this pattern and is deployed. Don't forget `library(RSQLite)` (or `duckdb`) explicitly — `QueryChat$new()`'s `DataFrameSource` needs a database engine at runtime and rsconnect only bundles packages it sees named in an actual `library()`/`::` call.

- **`03-ragnar` (formerly `11-ragnar`)**: a deep-dive on the [ragnar](https://ragnar.tidyverse.org/) RAG toolkit (`read_as_markdown`/`ragnar_find_links` → `markdown_chunk` → `embed_*` → `ragnar_store_create`/`ragnar_store_ingest` → `ragnar_retrieve_vss`/`ragnar_retrieve_bm25` → `ragnar_register_tool_retrieve`), trained live on R4DEV's own published site. Most chunks **actually execute at render time** (not `eval: false`) because `embed_ollama()` needs no API key/quota — Ollama is installed locally with `embeddinggemma`/`nomic-embed-text` pulled. Only the multi-page store-build/retrieve/tool-calling chunks are `eval: false` (would re-crawl + re-embed hundreds of chunks on every render otherwise), with real captured output pasted in. The **"Ask R4DEV" capstone** (`shiny/r4dev-ask`) lives at the end of this session (moved out of `10-llm-apps`) and is built with ragnar's own store/ingest functions. It still retrieves with **`ragnar_retrieve_bm25()`, not VSS**, in production: the store was built locally with `embed_ollama()`, but Connect Cloud can't reach a local Ollama instance to embed a live user question, and no cloud embedding provider has usable quota yet (`OPENAI_API_KEY`: `insufficient_quota`; no Gemini key) — a one-line swap to `embed_google_gemini()` fixes it the moment that changes. Rebuild the store with a script equivalent to `shiny/r4dev-ask/r4dev_ragnar.duckdb`'s build if session content changes significantly (`ragnar_store_create()` + `ragnar_store_ingest(store, urls, build_index = TRUE)`, then `INSTALL vss; LOAD vss;` before any `CHECKPOINT`).
- **`ragnar` gotcha**: `ragnar_store_inspect()` launches an **interactive Shiny viewer** — calling it in a non-interactive `Rscript` hangs forever waiting for a browser connection that never comes. Never call it outside an interactive session; inspect a store's contents with plain SQL/dplyr instead.
- **Posit Connect Cloud**: `rsconnect` is pre-authenticated on this machine for account `nelsonamayad` (`connect.posit.cloud` and `shinyapps.io` both). Footguns hit during deployment, worth remembering: (1) `.Renviron` lives at the non-standard `~/Documents/.Renviron` — a plain `Rscript` does **not** auto-source it (base R looks at `HOME`), so any script needing those keys must call `readRenviron("~/Documents/.Renviron")` explicitly first. (2) Redeploying an app under the same `appId` after fixing a *missing package* error can silently reuse a stale cached server-side environment that still lacks the package — delete the local `shiny/<app>/rsconnect/` folder and deploy under a fresh `appName` to force a clean rebuild. (3) `rsconnect::purgeApp()`/`terminateApp()` only support `shinyapps.io` — there is no programmatic way to delete Connect Cloud content; removed apps leave an orphaned deployment that needs manual deletion via the dashboard. (4) On Windows, killing a backgrounded R process by its bash-tool PID does not always kill the underlying native `Rscript.exe` — orphaned processes can keep files locked; use `taskkill //F //PID <pid>` (from `tasklist`) if a script hangs and a later run reports a DuckDB/file-in-use error.
- **⚠️ Connect Cloud iframe gotcha (important, bit us for a full deploy round)**: the URL `rsconnect::deployApp()` prints (`connect.posit.cloud/<user>/content/<id>`) sends `X-Frame-Options: SAMEORIGIN` — **every browser refuses to render it in an iframe from another origin**, including from this Netlify site. An app embedded with that URL returns HTTP 200 and works fine visited directly, but is silently blank wherever it's iframed — this affected every single embedded app on the site at once, not just one. The fix: Connect Cloud has a separate `https://<owner>-<app-slug>.share.connect.posit.cloud/` URL per app that does not appear to send the same header, set via a manual "Share"/custom-URL control in the Connect Cloud dashboard (no API/`rsconnect` access to set or read it — the account owner has to do this by hand per app and report the resulting URL back). **Always use the `*.share.connect.posit.cloud` URL for any `<iframe src>` on this site, never the plain `content/<id>` one.**
- **`terra`/GDAL build failure — root cause (killed r4dev-covid19, blocks any leaflet app)**: `terra` 1.9-34 (current CRAN release) fails to compile on both Connect Cloud's and shinyapps.io's build images because its C++ source calls a 3-arg `GDALMDArray::AsClassicDataset()` overload that doesn't exist in the GDAL 3.4.1 both platforms ship (only the 2-arg overload exists) — a real upstream version mismatch, not a code bug, and not fixable by avoiding specific R functions in app code. `sf` and `leaflet` both pull `terra` in (see above) regardless of whether the app ever touches polygon geometry. One contributing wrinkle also worth remembering: **`rsconnect`'s dependency scanner reads every `.R` file in the app directory, not just the one Shiny actually runs** — a leftover legacy `app_2022.R` in `r4dev-covid19`'s folder was silently dragging `terra` back into the manifest even after the live `app.R` had dropped `sf`/`leaflet`. Delete stray legacy `.R` files from any `shiny/<app>/` folder before deploying. Also remember the stale-cached-environment footgun above still applies on top of this — a redeploy under the same `appId` can report the old terra error with no new build log; deploying under a fresh `appName` forces a real rebuild.
- **Local R package ABI mismatch (nanonext/mirai and others)**: this machine's R install (4.6.0) doesn't match the R version CRAN's current Windows binaries are built for (many packages — `nanonext`, `mirai`, `bslib`, `DT`, `RSQLite`, `shiny` — print "built under R version 4.6.1"). Usually harmless for pure-R packages, but severe for compiled/native ones: `nanonext` (mirai's low-level socket transport) crashed deterministically on a basic socket call. Fix that worked **without** changing R versions: `remove.packages(c("nanonext","mirai"))` then a clean `install.packages()` reinstall — the freshly-downloaded binaries resolved the deterministic crash. (An R 4.6.1 upgrade was attempted as the "real" fix but the installer failed silently under this shell — `/VERYSILENT` NSIS install exited code 2 with no log output, likely an admin-rights issue; not pursued further since the reinstall alone fixed the actual problem.) Separately, this session also hit a lot of *generic*, non-deterministic segfaults on completely unrelated trivial R calls (`split()` on a data frame, parsing a hardcoded JSON string) that had nothing to do with mirai/terra and simply succeeded on an identical retry — treat a single segfault on simple code as possibly transient and retry before concluding it's a real bug; only escalate on a *deterministic*, repeatable crash (as nanonext's was, until reinstalled).

- **APIs**: session 2 teaches APIs with `httr2` + Open-Meteo (keyless). Spotify content runs on a bundled archival snapshot (`spotify_favorites_archive.csv`) — the API died in Nov 2024 and this is framed as a reproducibility lesson. The same **scrape-once-save-snapshot** pattern is used for U2 lyrics (`06-scrap/u2_lyrics.csv`); prefer it whenever render-time scraping/API calls would be slow, rude, or rot-prone.
- **AI track (`sessions_ai/`, July 2026 restructure)**: the LLM sessions were split out of `sessions_workshop/` into their own top-level directory and renumbered — `09-llm` → `sessions_ai/01-llm`, `10-llm-apps` → `sessions_ai/02-llm-apps`, `11-ragnar` → `sessions_ai/03-ragnar`, plus a new `sessions_ai/04-agentic` (agentic coding: Claude Code, Codex, OpenClaw, Antigravity; agents/skills/MCP/permissions — prose-only, no executed chunks). Each moved `.qmd` carries an `aliases:` entry so old published `/sessions_workshop/...` URLs redirect. `01-llm` teaches ellmer (chat, structured extraction, tool calling); `02-llm-apps` teaches shinychat/querychat/ggsql. Teaching default is **Gemini free tier**, code is provider-agnostic; LLM chunks are `eval: false` with real captured outputs pasted in, so rendering never needs an API key. The ggsql chunks in 02-llm-apps DO execute (knitr engine, DuckDB, no key needed). Note the `r4dev-ask` ragnar store was ingested from the old `/sessions_workshop/` URLs — rebuild it (see the 03-ragnar note) next time content changes significantly.

## Gotchas

- Quarto may auto-detect the **broken R 4.4.1** install; renders must use R 4.6+ — set `QUARTO_R="C:/Program Files/R/R-4.6.0/bin"` if `quarto render` says "Unable to locate an installed version of R" (or remove the stale `C:\Program Files\R\R-4.4.1`).
- `project.render` in `_quarto.yml` **excludes** `MyBlog/`, `param_reports/`, `shiny/` — they are separate projects; don't remove the exclusions or the site render will descend into them (and `param_reports` currently fails to render — a known ⏳ item).
- LLM API keys live in `~/Documents/.Renviron` (never in code — the repo once leaked Spotify **and** Census credentials that way). They were later redacted from the repo's one existing commit via low-level git plumbing (`hash-object`/`write-tree`/`commit-tree`, not `filter-branch`) since this repo lives inside OneDrive and its sync layer stalls `git gc --prune=now`/`git repack` — expect those commands to time out or leave dangling unreachable blobs; that's local disk hygiene only (nothing reachable from a ref, so nothing clonable/pushable), not a sign the redaction failed.
- `_extensions/r-wasm/live/live.lua` line 1 carries a **local patch** (script-relative `require` for tinyyaml; Quarto 1.10/Windows breaks the upstream bare require). `quarto update r-wasm/quarto-live` will overwrite it — re-apply the patch block if `{webr}` chunks with `#|` options start failing with "attempt to call a nil value (field 'parse')".

## Commands

```sh
quarto preview                        # live-reload dev server for the site
quarto render                         # full site build → _blog/
quarto render sessions_workshop/02-plots/02-plots.qmd   # render one session
quarto publish netlify                # deploy (uses _publish.yml)
```

- `freeze: auto` is enabled: a render only re-executes R code in files whose source changed; results are cached in `_freeze/` (commit it). Executing a session still needs its R packages plus network access (sessions read data straight from URLs: OWID GitHub, Project Gutenberg, APIs, etc.), so prefer rendering the single file you changed.
- Shiny apps are run individually: `R -e 'shiny::runApp("shiny/affairs1969-sidebar")'` (each subfolder of `shiny/` is a standalone app with its own `app.R`).
- Parameterized reports: `param_reports/` is a **separate Quarto project** (own `_quarto.yml`, outputs to `param_reports/_reports/`); batch rendering is scripted in `param_reports/retractionwatch_create_reports.R`.
- `MyBlog/` is also a separate Quarto project — the demo blog students build in the publishing session. Don't merge its config with the root site.

## Structure

- `_quarto.yml` — site config: navbar (sessions are manually listed there, grouped into dropdown menus — Sessions / AI · LLMs / Thinking / Tools), theme `{light, dark}` pairing `[journal, brand]` with `respect-user-color-scheme: true` (adds an automatic light/dark toggle to the navbar), Google Analytics, hypothes.is comments, `execute: warning: false`. Output goes to `_blog/` (gitignored).
- `_brand.yml` / `_brand-dark.yml` — light/dark brand pair, wired via `_quarto.yml`'s `brand: {light, dark}`. Palette: `teal` #226F7F primary/navbar, `orange` #F75431 links, neutral **untinted** backgrounds (`paper` white / `abyss` near-black — deliberately not a pastel tint), plus `secondary`/`tertiary` roles for muted text and card surfaces. Fonts: Roboto Condensed (base/headings) + Fira Code (code), both Google Fonts. Reference palette/role names (e.g. `background: primary`) instead of repeating hex values elsewhere.
- `sessions_workshop/NN-name/NN-name.qmd` — the nine core lessons: 01-quarto … 08-reports plus `09-parallel` (purrr + mirai; renumbered from `12-parallel` in the July 2026 naming pass).
- `sessions_ai/NN-name/NN-name.qmd` — the AI · LLMs track: `01-llm` (ellmer), `02-llm-apps` (shinychat/querychat/ggsql), `03-ragnar` (RAG + "Ask R4DEV" capstone), `04-agentic` (agentic coding). Same session-file conventions as the workshop; has its own listing section on `index.qmd` and its own navbar dropdown.
- `sessions_thinking/NN-name/NN-name.qmd` — the Statistical thinking track (July 2026): `01-uncertainty` (simulation, sampling variation, LLN/CLT), `02-inference` (permutation + bootstrap with `infer`), `03-regression` (lm/broom, Anscombe, bootstrap uncertainty, regression to the mean), `04-causal` (DAGs with `ggdag`, confounder/collider simulations), `05-bayes` (moved from `sessions_workshop/13-bayes/bayes.qmd`; uses quarto-live). Sessions 1–4 fully execute at render (tidyverse + infer + ggdag + broom, penguins CSV from a public URL); card images are brand-colored ggplots generated once and committed. Own listing section + "Thinking" navbar dropdown.
- `sessions_tools/` — practice exercises (`01-practice`), resources (`02-resources`), feedback (`03-feedback`) — renumbered from 09/10/11 in the July 2026 naming pass. `01-practice` uses the r-wasm/live (quarto-live) extension for in-browser R exercises.
- `shiny/` — one subfolder per standalone app, all sharing the **`r4dev-*` naming convention** (`r4dev-collider`, `r4dev-ovb`, `r4dev-bayesapp`, `r4dev-ask`, `r4dev-affairs1969-navbar`/`-sidebar`; `r4dev-chat` was retired — see below) and the same logo (`www/r4dev_logo.png` in each app, copied from `logo/r4dev_dalle_1.png` — must live in `www/` since Shiny only serves static assets from there, not the app root). Every app is deployed to Posit Connect Cloud and embedded in its session as an `<iframe>` using the app's `*.share.connect.posit.cloud` URL (see the gotcha above) — **never link directly** to the personal Connect Cloud/shinyapps.io URL from a session page; the iframe is the only sanctioned way a showcased app appears on the site.
- **`r4dev-chat` was deliberately removed** (July 2026): it was a plain, ungrounded `shinychat` demo in `sessions_ai/02-llm-apps` that duplicated what `r4dev-ask` (the grounded RAG capstone in `sessions_ai/03-ragnar`) does better. `02-llm-apps` now teaches the same code as a download-only exercise with a callout pointing at the live capstone instead of embedding a second, redundant chat app.
- `index.qmd` — landing page; session cards are auto-generated Quarto **listings** over `sessions_workshop/`, `sessions_ai/`, `sessions_thinking/`, and `sessions_tools/`, so a new session appears there automatically but must be added to the navbar in `_quarto.yml` by hand. Every renamed/moved session keeps an `aliases:` entry so old published URLs redirect.
- `_extensions/` — vendored Quarto extensions: `r-wasm/live` (webR in-browser exercises, used by `sessions_tools/01-practice` and `sessions_thinking/05-bayes`; superseded `coatless/webr`, which was removed), `quarto-ext/shinylive`, `lightbox`, `fontawesome`, `shafayetShafee/downloadthis`. Update via `quarto add`, don't hand-edit (except the documented `live.lua` patch below).
- Data assets (PDFs, spreadsheets, GADM files, media) live **inside the session folder that uses them** — session code reads them via `paste0(getwd(), "/file")`, which resolves to the `.qmd`'s own directory during render. Don't add data files at the project root.

## Git / publishing workflow

- Work happens on `master` (local repo, no remote configured yet). Render outputs (`_blog/`, `MyBlog/_blog/`, `param_reports/_reports/`) are gitignored; `_freeze/` should be **committed** so renders on other machines reuse cached results instead of re-executing R.
- Deploys are manual: `quarto publish netlify` renders and pushes to the site in `_publish.yml`. There is no CI.

## Session file conventions

Each session `.qmd` follows the same pattern — keep it when editing or adding sessions:

- Frontmatter with `title`, `subtitle`, `description`, `categories`, `date`, `date-modified: last-modified`, an `image` (usually a gif in the session folder), and a `citation.url` pointing at the published page.
- Code uses the native pipe `|>`, explicit namespacing (`dplyr::mutate(...)`), and Quarto code annotations (`# <1>` with a matching numbered list below the chunk). Follows the tidyverse style guide.
- Prose is didactic, in English, with epigraph quotes, callouts (`callout-tip` etc.) and footnotes; data is imported from public URLs rather than bundled files where possible.
