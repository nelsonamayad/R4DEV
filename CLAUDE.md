# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

R4DEV is a Quarto website teaching reproducible data analysis in R (tidyverse-first), created by Nelson Amaya. Source lives at https://github.com/nelsonamayad/R4DEV and the site is published with GitHub Pages at https://nelsonamayad.github.io/R4DEV/ (served from the `gh-pages` branch). Netlify was dropped in October 2026; the old https://r4dev.netlify.app deploy was abandoned as-is, not redirected. Every lesson is a standalone `.qmd` that downloads real data from the web and builds plots, maps, animations, text analysis, simulations, LLM workflows, and Shiny apps.

The site has **three learning tracks plus tools — 20 lessons in total**:

| Track (navbar label) | Folder | Lessons | Overview page |
|---|---|---|---|
| Build with R | `sessions_workshop/` | 10 — `01-quarto`, `02-plots`, `03-text`, `04-topics`, `05-animate` … `09-reports`, `10-parallel` | `learn/build-with-r.qmd` |
| Work with AI | `sessions_ai/` | 4 — `01-llm`, `02-llm-apps`, `03-ragnar`, `04-agentic` (plus the "Ask R4DEV" capstone embedded in `03-ragnar`) | `learn/ai.qmd` |
| Think with data | `sessions_thinking/` | 6 — `01-uncertainty`, `02-inference`, `03-regression`, `04-causal`, `05-designs`, `06-bayes` | `learn/thinking.qmd` |
| Tools (not a track) | `sessions_tools/` | `01-practice`, `02-resources`, `03-feedback` | — |

Lessons are numbered per track (`NN-name/NN-name.qmd`, starting at 01). The roadmap and the history of how the site got here live in `UPDATE_PLAN.md`; the open content/site-quality backlog lives in `notes/content-restructure.md`.

## Commands

```sh
quarto preview                        # live-reload dev server for the site
quarto render                         # full site build → _blog/
quarto render sessions_workshop/02-plots/02-plots.qmd   # render one lesson
python checks/site_checks.py          # link/image/alt-text/nav-duplicate checks (after render)
python checks/generate_sitemap.py     # writes _blog/sitemap.xml (after render, before publish)
quarto publish gh-pages --no-render   # deploy _blog/ to the gh-pages branch (after render + checks)
```

- `freeze: auto` is enabled: a render only re-executes R code in files whose source changed; results are cached in `_freeze/` (commit it). Executing a lesson still needs its R packages plus network access (lessons read data straight from URLs: OWID GitHub, Project Gutenberg, APIs, etc.), so prefer rendering the single file you changed. Note that **any** edit to a file, even prose-only, re-executes all of its chunks — batch code edits to expensive lessons (03-text, 05-maps) deliberately.
- `checks/README.md` documents the site-quality checks (incl. a spellcheck word list, `checks/dictionary.txt`). Known false positive: `${href}` from the lightbox extension's inline JS.
- Shiny apps are run individually: `R -e 'shiny::runApp("shiny/affairs1969-sidebar")'` (each subfolder of `shiny/` is a standalone app with its own `app.R`).
- Parameterized reports: `param_reports/` is a **separate Quarto project** (own `_quarto.yml`, outputs to `param_reports/_reports/`); batch rendering is scripted in `param_reports/retractionwatch_create_reports.R`. Renders to HTML and PDF (PDF needs a TeX install; TeX Live is present). It needs `gapminder` and `rnaturalearthdata` installed — a missing `gapminder` was the whole cause of its long-standing "fails to render" status. Don't put a label in both the chunk header and `#| label:` (knitr warns on duplicates).
- `MyBlog/` is also a separate Quarto project — the demo blog students build in `01-quarto`. Don't merge its config with the root site.

Output goes to `_blog/` (gitignored).

A new lesson appears in its listing automatically, but **these are hand-maintained and must be updated too**: the navbar entry in `_quarto.yml`, the `.lesson-list` in the track's `learn/*.qmd` page, the lesson counts in `index.qmd` ("Three tracks, twenty lessons" and each track card's "N lessons"), the lesson count and "Estimated total time" line in the track's `learn/*.qmd` description and footer, and the recommended routes in `start.qmd` if relevant.
- `start.qmd` — "Start here": audience, prerequisites, install checklist, recommended routes (tabset).
- `learn/` — the three track overview pages (`build-with-r.qmd`, `ai.qmd`, `thinking.qmd`), each with a hand-written `.lesson-list` of `.lesson-row` links (title, outcome, level · duration).
- `about.qmd` — learning outcomes per track. `style.css` — site-wide custom CSS (masthead, track cards, lesson-list, `.lesson-info`, `.continue-learning`, feature cards). Uses Bootstrap CSS variables (`--bs-primary`, `--bs-link-color`, `--bs-body-color`) so both brands work without dark-mode overrides; **don't use `--bs-tertiary-color` for text** — in dark mode it resolves to a near-background charcoal (caused an invisible-card-text bug once).
- `_brand.yml` / `_brand-dark.yml` — light/dark brand pair. Palette: `teal` #226F7F primary/navbar, `orange` #F75431 accents, `rust` #C2401F light-mode links (orange itself is only 3.35:1 on white — fails WCAG AA for body text), neutral **untinted** backgrounds (`paper` white / `abyss` near-black — deliberately not a pastel tint), plus `secondary`/`tertiary` roles for muted text and card surfaces. The dark brand lifts `teal` to #4FB3C9 for text accents (7.3:1 on `abyss`), but white text on it is only 2.44:1, so `style.css` repaints the dark-mode navbar, footer and `.btn-primary` with the dark palette's `deepteal` (#226F7F, 5.76:1) via the `--brand-deepteal` CSS variable (Quarto exposes every palette colour as `--brand-<name>`; dark mode is `body.quarto-dark`). Check any new colour pairing against WCAG AA (4.5:1 for body text). Fonts: Roboto Condensed (base/headings) + Fira Code (code). Reference palette/role names instead of repeating hex values. Don't add a `color: link:` field — the `brand.yml` R package doesn't accept it (link colour belongs under `typography.link.color`) and it crashes any `bslib::bs_theme()` call in the repo's Shiny apps, since `bs_theme()` walks up parent dirs to find `_brand.yml`.

Every edited lesson re-executes on the next render.

## Lesson file conventions

Every lesson `.qmd` follows the same pattern — keep it when editing or adding lessons:

- **Frontmatter**: `title` (ends in an emoji), `subtitle`, `author`, `description`, `categories`, `date`, `date-modified: last-modified`, `order` (position within its track — drives listing sort), `level` (Beginner/Intermediate/Advanced), `duration` (e.g. `90 min`), `track`, `prerequisites`, `image` (usually a gif in the lesson folder), `citation.url` pointing at the published page, and `aliases:` if the file ever moved. Tools pages carry `order` too.
- **Page skeleton**: a `.lesson-info` div (level/time/prerequisites/tools) and a `## You will learn to` list (3–5 objectives) near the top; content in `## PART I/II/…` sections (often `{-}` unnumbered) with optional `## Bonus track` sections; then `## 🏗 Practice N: <name> {.unnumbered}`, `## Key takeaways` (3–5 points), a `.continue-learning` footer (previous / track overview / next — track-final lessons point sideways at another track), and `## References` last if present.
- **Code**: native pipe `|>`, explicit namespacing (`dplyr::mutate(...)`), tidyverse style guide, Quarto code annotations (`# <1>` with a matching numbered list). Put the annotation list **immediately after the code chunk**, before any pasted `#>` output block — otherwise Quarto warns "List item N has no corresponding annotation".
- **Prose**: didactic, in **British English** (analyse, visualise, colour…) except where prose names a same-spelled code argument (`color =`), with epigraph quotes, callouts and footnotes. Data is imported from public URLs where possible; use the **scrape-once-save-snapshot** pattern (e.g. `02-plots/spotify_favorites_archive.csv` — the Spotify API died Nov 2024, framed as a reproducibility lesson; `06-scrap/u2_lyrics.csv`) whenever render-time scraping/API calls would be slow, rude, or rot-prone.
- **LLM chunks** are `eval: false` with real captured output pasted in, so rendering never needs an API key. Teaching default is the **Gemini free tier**, code is provider-agnostic via ellmer. Exceptions that execute live: the ggsql chunks in `02-llm-apps` (knitr engine + DuckDB) and most of `03-ragnar` (`embed_ollama()` against a local Ollama with `embeddinggemma`/`nomic-embed-text` — no key or quota; only the multi-page store-build/retrieve/tool-calling chunks are `eval: false`).
- **Practice sections**: `## 🏗 Practice N: <name> {.unnumbered}`, numbered per track to match the lesson number, holding three collapsed tier callouts — Basic (`callout-note`), Intermediate (`callout-important`), Advanced (`callout-caution`). On quarto-live lessons, Basic/Intermediate are runnable `{webr}` chunks with `#| exercise: ex_<w|a><NN>_<tier>` ids (site-unique), `______` blanks and `.hint`/`.solution` divs (outer tier fences use 5 colons to allow nesting); Advanced is always prose for own-machine work (keys, network, deployment). Lessons without quarto-live (workshop 01/08/09, AI 02/04, thinking 01–05) use the same three tiers as prose bullets. Add any new anchor to `sessions_tools/01-practice`.
- **In-browser R (quarto-live)**: `format: live-html` + `engine: knitr` + an `{{< include /_extensions/r-wasm/live/_knitr.qmd >}}` line + `{webr}` chunks, used on 11 pages: workshop 02/03/04/05/06/07/10, AI 01/03, `sessions_thinking/06-bayes`, `sessions_tools/01-practice`. Verify every new exercise's solution in local R before shipping. Data files for `{webr}` chunks go in a **top-level `resources:`** YAML key (not `webr: resources:` — only the former is copied to `_blog`); wasm packages download lazily on first *Run Code*, so even `sf` costs nothing at page load; exercises work inside `collapse="true"` callouts.
- **OJS explainers**: `{ojs}` cells (sometimes with R pre-computing data via `ojs_define()`) — in `05-animate`'s bonus track and `sessions_thinking/04-causal` + `05-designs`. OJS names are page-global and order-independent, so shared helper cells (`C` palette, `drawDAG`, `fmt`, `olsFit`, `tiles`) must exist on **every page that uses them** — both causal lessons carry their own copies, marked `//| output: false`.

Rules and footguns:

- **Iframe-only policy**: a showcased app appears on the site only as an `<iframe>`, never as a direct clickable link to the personal Connect Cloud/shinyapps.io account.
- **⚠️ Always iframe the `https://<owner>-<slug>.share.connect.posit.cloud/` URL**, never the `connect.posit.cloud/<user>/content/<id>` URL `rsconnect::deployApp()` prints — the latter sends `X-Frame-Options: SAMEORIGIN`, so it works when visited directly but is silently blank inside an iframe (this once blanked every app on the site). The share URL is set by hand in the Connect Cloud dashboard ("Share"/custom URL; no API) — the account owner has to create it and report it back. Verify with `curl -s -o /dev/null -w "%{http_code}" <share-url>`: an existing share URL returns 200, one that hasn't been created yet returns 404.
- `rsconnect` is pre-authenticated on this machine for account `nelsonamayad` (both `connect.posit.cloud` and `shinyapps.io`).
- **Stale server environments**: redeploying under the same `appId` after fixing a *missing package* error can silently reuse the old broken environment. Delete the local `shiny/<app>/rsconnect/` folder and deploy under a fresh `appName` to force a clean rebuild — which leaves the previous content ID orphaned on Connect Cloud.
- **No programmatic delete on Connect Cloud**: `rsconnect::purgeApp()`/`terminateApp()` only support shinyapps.io. Orphans need manual dashboard cleanup. Once an app *is* deleted in the dashboard, a redeploy from its folder fails with "Failed to find existing content on server" — delete the local `rsconnect/` folder and deploy again.
- **rsconnect bundles only packages it sees in `library()`/`::` calls, and scans every `.R` file in the app folder** — a stray legacy `.R` file (e.g. an old `app_2022.R`) can drag dead dependencies into the manifest. Keep each app folder to `app.R` + `www/` + data. Conversely, runtime-only dependencies must be named explicitly (e.g. `library(RSQLite)` for querychat's `DataFrameSource`).
- **`terra`/GDAL wall — blocks `sf` and `leaflet` on both hosts**: `terra` ≥ 1.8-54 calls a 3-arg `GDALMDArray::AsClassicDataset()` that doesn't exist in the GDAL 3.4.1 both Connect Cloud and shinyapps.io ship, so it fails to compile. `leaflet` hard-`Imports` `sf` (and Suggests `terra`), so even a points-only `library(leaflet)` app fails. Use `plotly` `scattergeo`/`choropleth` instead: it draws its own basemap with no geospatial packages and is proven to deploy (`r4dev-earthquakes`, October 2026). Pinning `terra` ≤ 1.8-53 via an `renv.lock` deploy should also work in principle, but a local `remotes::install_version("terra", ...)` downgrade crashed silently when tried. This affects deployed apps only — `06-maps`' static/htmlwidget leaflet output renders fine.
- **querychat**: don't deploy `querychat_app()` — its `$app()` calls `shiny::runGadget()`, which binds its own port and fails the host's health check. Use the modular API: `QueryChat$new(data, ..., client = ellmer::chat_anthropic(model = "claude-sonnet-5"))` + `qc$sidebar()`/`qc$ui()` + `qc$server()` inside an ordinary `page_sidebar()`/`shinyApp()`.
- **Deployed apps run on `ANTHROPIC_API_KEY`** (set as a Connect Cloud env var, never in code) even though lessons teach Gemini — no Gemini key has been provisioned.
- **`r4dev-ask`** uses ragnar's store (`shiny/r4dev-ask/r4dev_ragnar.duckdb`) with **`ragnar_retrieve_bm25()`, not VSS**: the store was embedded locally with `embed_ollama()`, and Connect Cloud can't reach a local Ollama to embed live questions; no cloud embedding provider has quota (`OPENAI_API_KEY`: `insufficient_quota`; no Gemini key). Swapping to `embed_google_gemini()` + `ragnar_retrieve_vss()` is a one-line change once a key exists. `ragnar_store_connect()` needs no `embed` function, which is what makes BM25-only deployment work. Current store (6 October 2026): 567 chunks from 27 pages; `about.html` is missing because ragnar 0.3.1's chunker errors on it (`findInterval: 'vec' must be sorted`), a known gap. **Rebuild it** with `Rscript shiny/build_r4dev_ask_store.R` (crawls the published site's sitemap, embeds with local Ollama, builds into a temp file and swaps it in), then redeploy, whenever content changes significantly. The script needs the site to be live at github.io first. Under the hood: `ragnar_store_create()` + `ragnar_store_ingest(store, urls, build_index = TRUE)`, and `INSTALL vss; LOAD vss;` before any `CHECKPOINT`. ragnar 0.3.1 shells out to `markitdown` via `uv` on first use (it downloads ~50 Python packages once).
- **`ragnar_store_inspect()` launches an interactive Shiny viewer** — in a non-interactive `Rscript` it hangs forever. Inspect stores with plain SQL/dplyr instead.

## Gotchas (local environment)

- **R versions**: this machine has R 4.6.0 (use it) and a stale, broken R 4.4.1 that Quarto may auto-detect. If `quarto render` says "Unable to locate an installed version of R", set `QUARTO_R="C:/Program Files/R/R-4.6.0/bin"` (or remove the leftover — it is only a 64 MB remnant with an empty `bin/` and no uninstaller, and deleting it needs an elevated shell: `Remove-Item -Recurse -Force "C:\Program Files\R\R-4.4.1"`). Quarto is 1.10.x.
- **Package ABI mismatch**: many CRAN Windows binaries print "built under R version 4.6.1". Harmless for pure-R packages; for compiled ones a deterministic crash is fixed by `remove.packages()` + a clean `install.packages()` (this fixed `nanonext`/`mirai`). Upgrading R via the silent NSIS installer failed under this shell (exit code 2, likely admin rights); the user chose to stay on 4.6.0. Separately, trivial R calls occasionally segfault once and succeed on an identical retry — retry before treating a single crash as a real bug, and prefer running a `.R` script file over long `Rscript -e '...'` one-liners.
- **Secrets**: API keys live in `~/Documents/.Renviron` (non-standard location — a plain `Rscript` does **not** load it; call `readRenviron("~/Documents/.Renviron")` first). The cause: Git Bash sets `HOME=C:\Users\nelso`, so R looks for `~/.Renviron` there. Before `quarto render` (e.g. `06-maps` needs `CENSUS_API_KEY`), `export R_ENVIRON_USER="C:/Users/nelso/Documents/.Renviron"`, or the render stops with a `get_census_api_key()` error. Never put keys in code: the repo once leaked Spotify and Census credentials. They were redacted from history with low-level git plumbing (`hash-object`/`write-tree`/`commit-tree`), not `filter-branch`.
- **OneDrive**: the repo lives in a live-synced OneDrive folder. `git gc --prune=now`/`git repack` stall or leave dangling unreachable blobs (local hygiene only, not a leak). `quarto render`'s final move into `_blog/` occasionally fails with `rename ... os error 2` / `ERROR: NotFound` when OneDrive holds a lock — just re-run (the freeze cache makes the retry fast).
- **Orphaned R processes on Windows**: killing a backgrounded R job by its bash-tool PID may leave the native `Rscript.exe` running and holding files (DuckDB "file already used by another process"). Use `tasklist` + `taskkill //F //PID <pid>`.
- `_extensions/r-wasm/live/live.lua` line 1 carries a **local patch** (script-relative `require` for tinyyaml; Quarto 1.10/Windows breaks the upstream bare require). `quarto update r-wasm/quarto-live` will overwrite it — re-apply the patch if `{webr}` chunks with `#|` options fail with "attempt to call a nil value (field 'parse')".
- `project.render` in `_quarto.yml` **excludes** `MyBlog/`, `param_reports/`, `shiny/` — they are separate projects; don't remove the exclusions.
- `geom_path()`/`geom_line()` connect points in **row order**: after any `group_by()`/`summarise()`, `arrange()` by group and x before plotting (this once blanked the Maddison ggiraph plot in `02-plots`).
- No browser tooling is installed in the project. Visual checks (dark mode, mobile width) have been done ad hoc with Playwright installed into the scratchpad, not as a project dependency.

## Git / publishing workflow

- Work happens on `main`, pushed to `origin` = https://github.com/nelsonamayad/R4DEV (public). Local history was rewritten in October 2026 to drop an unused 120 MB `05-maps/kontur_population_FR_20231101.gpkg` (GitHub rejects files over 100 MB); it is now gitignored and kept on disk only. Never commit files over 100 MB. Render outputs (`_blog/`, `MyBlog/_blog/`, `param_reports/_reports/`) are gitignored; `_freeze/` is **committed** so renders elsewhere reuse cached results.
- Deploys are manual: `quarto render`, then `python checks/site_checks.py` and `python checks/generate_sitemap.py`, then `quarto publish gh-pages --no-render`. There is no CI: the lessons need local R packages, network access, local Ollama (03-ragnar) and keys, so GitHub Actions rendering isn't practical.
- The site lives under a **subpath** (`/R4DEV/`): links in markdown that start with `/` are rewritten by Quarto, but raw-HTML `href="/..."`/`src="/..."` are not and will 404. `robots.txt` at `/R4DEV/robots.txt` is ignored by crawlers (only domain-root robots count); submit the sitemap in Google Search Console instead.
- `.gitattributes` forces `*.qmd` to LF. The freeze hash is the md5 of the raw `.qmd` bytes, so a CRLF checkout (`core.autocrlf=true` on this machine) would silently invalidate every freeze and re-execute everything.
- Teaching content about Netlify (01-quarto: students publish *their own* blog there) is unrelated to where R4DEV is hosted; it stays.
